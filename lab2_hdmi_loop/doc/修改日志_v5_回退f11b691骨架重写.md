## 1. v4.1 里被删掉的东西（无信号的可疑源）

| 被删的部件 | 为什么删 |

| `video_core` 里的 **输入弹性 FIFO**（16 深 24bit，异步读） | 灰度通路里唯一的"新东西"，f11b691 没有；异步读 LUTRAM 的数据/valid 相位如果有人为差错就会整条流水线起不来 |

## 5. v5.1 修复：高斯模式无信号的根因与处理

### 5.1 根因（仿真可复现）

灰度模式上板正常、切到高斯模式就"无信号"，差别不在同步，而在**高斯核把灰度核的 `src TREADY` 每行顶住 1 拍**：

```
CH-B gauss，修复前：DE/line min/max = 0/1919   ← 每行少 1 个像素
CH-B gauss，修复后：DE/line min/max = 0/1920   ← 每行完整 1920
```

少这 1 个像素看起来无所谓，但 `gauss3x3` 是"平铺计数器"结构，一帧要推进 **2076601** 次
（= 1080 行 ×(1920 读 + 1 补) + 帧末补 0 行 1921）。丢 1080 个像素/帧后它每帧只推进
**2075520** 次，比应该的少 1081 次 → **核的行/场相位逐帧漂移**（约 0.56 行/帧），
几帧之后核的"第 0 行不出数"就漂进可见区 → 每帧的有效行结构不规整 → **采集卡锁不住 → 「无信号」**。

### 5.2 处理

弹性 FIFO **只加在高斯分支**（`generate` 里两份独立的 `rgb2gray` 例化）：

```verilog
if (EN_GAUSS != 0) begin : g_gauss        // 弹性 FIFO → rgb2gray → gauss3x3
    ...
end else begin : g_no_gauss               // = f11b691 逐字一致（无 FIFO）
    rgb2gray u_rgb2gray(.src_V_V_TDATA(rgb_in), ... .dst_V_V_TREADY(smooth_ready));
    assign smooth_out = gray_out; assign smooth_valid = gray_valid;
end
```

这样灰度模式**一个门都没变**（资源仍 568 LUT / 657 FF），高斯模式则拿到完整的 1920 像素/行，
计数器每帧正好走完 2076601 次 → **帧锁定，不再漂移**。

## 5.4 v5.2：MODE=1/2 都无信号的两处真 bug + 按用户要求去掉 for 循环

### (1) `video_sync.v`：always 里不再用 for（用户要求）

```verilog
// 旧：reg [1:0] sync_dly [0:LATENCY-1] + always 里 for 循环（复位分支要遍历 LATENCY 个寄存器）
// 新：一个 packed 向量，每拍一次非阻塞移位，无 for、无复位
reg [2*LATENCY-1:0] sync_sr;
always @(posedge clk)
    sync_sr <= {sync_sr[2*LATENCY-3:0], hs_in, vs_in};

assign hs_out = sync_sr[2*LATENCY-1];
assign vs_out = sync_sr[2*LATENCY-2];
```

效果（综合实测，LATENCY=2206）：

| 指标 | for + 复位版 | 本次（packed、无复位） |
|---|---|---|
| LUT as Shift Register | 138 | **138**（都是 SRL） |
| Slice Registers | 3225 | **1013** ↓ |
| 大链复位扇出 | 2206 个寄存器同时复位 | **无** |

> 移位链没有复位：上电后 2206 拍（≈15µs）内输出是移位进来的旧值，之后自然正确；
> 这期间编码器还没被采集卡锁定，无影响。`video_sync` 也因此删掉了 `rst_n`/`de_in` 端口。

### (2) 弹性 FIFO 放在**两个核之间**，灰度核 dst 恒不反压

```verilog
if (EN_GAUSS != 0) begin : g_gauss
    rgb2gray u_rgb2gray( ... .dst_V_V_TREADY(1'b1) );   // 灰度核与灰度模式完全一致
    // 8bit × 16 深 FIFO：写 = gray_valid，读 = 高斯核 src TREADY & ~fifo_empty
    gauss3x3 u_gauss3x3( .src_V_V_TDATA(fifo_dout), .src_V_V_TVALID(fifo_valid), .src_V_V_TREADY(gauss_src_rdy), ... );
end else begin : g_no_gauss
    rgb2gray u_rgb2gray( ... .dst_V_V_TREADY(smooth_ready) );   // = f11b691
    assign smooth_out = gray_out; assign smooth_valid = gray_valid;
end
```

两处必改的细节：

1. **读使能必须带"非空"**：`fifo_rd = gauss_src_rdy & ~fifo_empty;`
   第一版漏了这个 `& ~fifo_empty`，空转时读指针一直加 → 计数器下溢 → 误判"满" → 灌爆 FIFO，
   仿真里立刻报 `灰度→高斯 FIFO 溢出`。修掉后 `DE/line = 1920`、溢出 0。
2. 灰度核 dst 不反压 → 高斯核再怎么顶，也**影响不到灰度通路**。

### (3) MODE=2 之前为什么也会无信号（综合日志证据）

MODE=2 时高斯核的输出没人用，综合器会把它**整块删掉**（日志：`Synth 8-3332 ... unused and will be
removed`，且 BRAM 从 1 变 0）。而旧结构里 `gray_r`（灰度核 dst TREADY）正是由高斯核的 `src TREADY` 驱动的
→ 高斯核被删后这根线没人驱动 → 灰度核永远吐不出数据 → DE 恒 0 → **无信号**。
新结构里灰度核 dst 是常数 `1'b1`，不再依赖高斯核，所以 **MODE=2 现在是可靠的诊断档位**。

## 5.5 v5.3：HS/VS 同步缓存改用 FIFO IP 核（2bit × 4096）

### 5.5.1 IP 配置（工程内 `sync_fifo_2x4096`）

| 项 | 值 |
|---|---|
| VLNV | `xilinx.com:ip:fifo_generator:13.2` |
| Interface / Clock | Native / Common Clock |
| 实现 | **Common Clock Block RAM**（占 1 个 BRAM18） |
| 数据宽度 / 深度 | **2 bit / 4096** |
| 读模式 | **First Word Fall Through**（dout 一直可见表头） |
| 复位 | Synchronous Reset（`srst`） |
| 数据计数 | **`Data_Count = true` → 输出 `data_count[12:0]`**（做"水位出队"必需） |

> 注意：FIFO Generator 13.2 里 `Read_Data_Count` 默认是 disabled 参数，
> 直接设它会被忽略（`IP_Flow 19-3374`）；要先打开总开关 `CONFIG.Data_Count {true}`，
> 端口就变成统一的 `data_count[12:0]`。

端口：`clk, srst, din[1:0], wr_en, rd_en, dout[1:0], full, empty, data_count[12:0]`

### 5.5.2 当"固定延迟线"用

```verilog
wire [12:0] fifo_cnt;
wire        fifo_we = rst_n;                    // 每拍写一次 {hs,vs}（复位期间不写）
wire        fifo_re = (fifo_cnt >= LATENCY);    // 水位到 LATENCY 才出队 → 固定延迟

sync_fifo_2x4096 u_sync_fifo (
    .clk(clk), .srst(~rst_n),
    .din({hs_in, vs_in}), .wr_en(fifo_we), .rd_en(fifo_re),
    .dout({hs_out, vs_out}), .full(), .empty(), .data_count(fifo_cnt)
);
```

4096 深可缓存 **1.8 个 1080p 行周期**（2200 拍/行），高斯那档用 2206 拍余量足够。

### 5.5.3 统一：两种模式都走 FIFO（v5.4，按用户意见改）

最初按"小延迟用移位链、行级延迟用 FIFO"分两档，理由是与已上板验证的灰度版本保持一字不差。
但分两档的代价是**同一份代码有两种行为**，且 FIFO 通路只在一种模式下被验证。改为**统一只保留 FIFO 一条实现**：

| 模式 | LATENCY | 同步缓存 |
|---|---|---|
| 灰度 MODE=0 | 3 | `sync_fifo_2x4096`（水位 3） |
| 平滑 MODE=1 | 2206 | `sync_fifo_2x4096`（水位 2206） |

```verilog
wire fifo_we = rst_n;                     // 每拍写 {hs,vs}
wire fifo_re = (fifo_cnt >= LATENCY);     // 水位出队 → 固定延迟
sync_fifo_2x4096 u_sync_fifo(.clk(clk), .srst(~rst_n), .din({hs_in,vs_in}),
                             .wr_en(fifo_we), .rd_en(fifo_re),
                             .dout({hs_out,vs_out}), .full(), .empty(),
                             .data_count(fifo_cnt));
```

**实测代价几乎为 0**（2bit 窄位宽的 FIFO 综合器主要放进分布式 RAM，不占 BRAM）：

| 配置 | LUT | FF | BRAM Tile |
|---|---|---|---|
| 灰度 + 移位链（旧） | 568 | 657 | 0 |
| **灰度 + FIFO（新）** | **572** | **651** | **0** |
| 高斯 + SRL 链（旧） | 1005 | 1013 | 1 |
| **高斯 + FIFO（新）** | **873** | **1015** | 1（高斯行缓存；另有 2 个 RAMB18E1） |

好处：只有一条路径、灰度模式也顺便验证 FIFO；以后把 `fifo_re` 门限换成寄存器（VIO 驱动）就能**上板实时标定延迟**，不必重新综合。

## 8. v5.5：核例化改为"两核都在 + 输出多路选择"（不用 generate）

### 8.1 `video_core.v` 新结构

```
rgb_in/de_in ──> rgb2gray ──[8bit×16 弹性 FIFO]──> gauss3x3
                     │                                   │
                     │gray_out/gray_valid                │gauss_out/gauss_vld
                     └──────────────┬────────────────────┘
                                    ▼
                        多路选择器 sel_gauss ──> smooth_out / smooth_valid
```

```verilog
// 两个核都例化（没有 generate、没有条件例化）
rgb2gray  u_rgb2gray (... .dst_V_V_TREADY(1'b1) );     // 灰度核 dst 永不反压
gauss3x3  u_gauss3x3 (... .src_V_V_TDATA(fifo_dout), .src_V_V_TVALID(fifo_valid),
                            .src_V_V_TREADY(gauss_src_rdy) );

// 输出多路选择
assign smooth_out   = sel_gauss ? gauss_out : gray_out;
assign smooth_valid = sel_gauss ? gauss_vld : gray_valid;
```

* 端口变化：**删掉参数 `EN_GAUSS`，新增输入端口 `sel_gauss`**（1=显示平滑，0=显示灰度）

### 8.2 为什么这样更好

2. 以后做任务四的按键切换，只要把 `sel_gauss` 接到按键（或 VIO 寄存器）即可——**切换时两个核都在跑，只是换多路选择器的输入**，不会出现"切模式把核停了"的问题；

## 9. v5.6【根因】像素时钟没有约束 → 高斯核在板上跑飞

### 9.1 现象

`MODE=0`（灰度）画面正常，`MODE=1`（高斯）**无输出**；仿真全过、综合 0 错。

### 9.2 定位过程（都是实测量出来的）

1. `report_clocks`（实现后）：

```
Clock          Period(ns)  Attributes  Sources
sys_clk        20.000      P           {sys_clk}
clkfbout_mmcm  20.000      P,G,A       {...CLKFBOUT}
clk_out1_mmcm  100.000     P,G,A       {...CLKOUT0}      ← 10MHz（i2c_edid）
clk_out2_mmcm  5.000       P,G,A       {...CLKOUT1}      ← 200MHz
clk_hdmi_in_p  6.000       V           {}                ← 虚拟时钟（差分对，没落到网络）
```

**没有 `pixel_clk`！** 也就是说从 HDMI 输入 TMDS 恢复出来的 148.5MHz 像素域
（`rgb2gray` / `gauss3x3` / `video_sync` / `dvi` 编码）**全部是"未约束路径"**，
P&R 完全不为 148.5MHz 做优化。

2. 在已布线的网表上补一条 `create_clock -period 6.734 -name pixel_clk [get_nets pixel_clk]`
   再量 slack → **我们自己的逻辑 WNS = −2.233 ns**，最差路径就在高斯核里：

```
-2.233ns  u_video_core/u_gauss3x3/i_reg_214_reg[4]/C
       -> u_video_core/u_gauss3x3/wlb_lb_val_V_1_U/.../ram_reg/ENBWREN
-2.233ns  u_video_core/u_gauss3x3/i_reg_214_reg[4]/C
       -> u_video_core/u_gauss3x3/col_assign_fu_112_reg[*]/CE
```

`video_core / video_sync` 内共 **311 条违例路径**。

3. 为什么灰度能动：灰度通路只有 RGB→灰度（3 级流水）+ 很浅的组合逻辑，
   即使被乱摆也能在 148.5MHz 逮住；高斯核带 BRAM 行缓存 + 卷积加法树 + `col` 逻辑，
   未约束时必然崩。**这就是"仿真全过、上板只有灰度能动"的真正原因。**

### 9.3 修复（`constrs_1/new/hdmi_loop.xdc` 追加）

```tcl
create_clock -period 6.734 -name pixel_clk [get_nets pixel_clk]

set_clock_groups -asynchronous \
    -group [get_clocks -of_objects [get_nets pixel_clk]] \
    -group [get_clocks clk_out1_mmcm] \
    -group [get_clocks clk_out2_mmcm]

set_false_path -to [get_pins -hierarchical -filter {REF_PIN_NAME == R || REF_PIN_NAME == S}]
```

### 9.4 修复后重跑 综合 + 实现（MODE=1）

```
From Clock: pixel_clk  To Clock: pixel_clk
Setup : 0 Failing Endpoints,  Worst Slack  +1.409ns
Hold  : 0 Failing Endpoints,  Worst Slack  +0.084ns
（clk_out2_mmcm：+1.817ns；clk_out1_mmcm：+95.9ns；全部 MET）
```

比特流已生成：`hdmi_loop.runs/impl_1/hdmi_loop.bit`（2.1MB）。

> 教训：这个基座工程（正点原子 HDMI 环回）原 XDC 只约束了 `sys_clk` 和差分输入时钟，
> **像素域一直没约束**。环回直通/灰度这种浅逻辑碰巧能跑，一接带行缓存的 HLS 核就必崩。
> 以后任何像素域时序问题都先看 `pixel_clk` 组；`pixel_clk_5x`（742.5MHz，只给 OSERDES 用）暂未约束。

## 10. v5.7：HS/VS 延迟改用精确移位链（SRL），弃用 FIFO+data_count

### 10.1 为什么换

板上实测（LED 指示）暴露两个问题：

1. **高斯核其实在正常工作**——`gauss_beats != 0` 的 LED 常亮，说明核每帧都在出数；
2. `video_sync` 用 `sync_fifo_2x4096` + `data_count >= LATENCY` 做 2205 拍延迟时，
   以 hs 为界统计出来的"每行 DE 拍数"两路都不等于 1920（连已知正常的灰度路也不对），
   说明 **`data_count` 水位这条延迟线在大延迟下不可靠**，hs/vs 的节拍本身被破坏了，
   显示器自然锁不住。

### 10.2 新实现（`video_sync.v`）

```verilog
// DE 与像素永远跟核的 TVALID/TDATA
assign de_out  = gray_valid;
assign rgb_out = {3{gray_in}};

// HS/VS 精确延迟 LATENCY 拍：packed 移位链（无 for、无复位）
reg [2*LATENCY-1:0] sr;
always @(posedge clk) sr <= {sr[2*LATENCY-3:0], hs_in, vs_in};
assign hs_out = sr[2*LATENCY-1];
assign vs_out = sr[2*LATENCY-2];
```

* 综合器识别为 **SRL32E 链**：2205 拍只需约 140 个 LUT（总 FF 3739 < 4410，反证没有变成触发器阵列）
* 延迟**严格等于** `LATENCY`（FIFO 版本会多 1~2 拍，且依赖 `data_count` 语义）
* 不加复位：加了就退化成触发器阵列，且复位会清空延迟内容；Xilinx 上电初值为 0，安全
* `sync_fifo_2x4096` IP 保留在工程里但**不再被例化**（BRAM 占用从 4.5 → 4）

### 10.3 验证

|---|---|
| 同步自检 CH0(3) / CH1(2205) | 6653 / 8855 拍，**0 错** → PASS（延迟精确等于 LATENCY） |
| 系统检查 CH-A 灰度 | hs 30/30、vs 2/2、DE/line 1920、像素 0 错 → PASS |
| 系统检查 CH-B 高斯 | hs 29/30、vs 2/2、DE/line 1920、DE&VS=0 → PASS |

## 11. v5.8：显示时序改为"定长延迟 + 像素 FIFO"，与核抖动解耦

### 11.1 动机

板上反复出现"高斯核有出数（LED 常亮）但 MODE=1 无画面"。根因是**编码器拿到的 DE 直接来自核的 TVALID**：
高斯核内部每行要做 1921 次流水推进（1920 读 + 1 行末补 0），所以它的 DE 天生带气泡、相位有抖动；
而 HS/VS 是固定延迟 —— 两者相对位置不稳，显示器/采集卡锁不住。

### 11.2 新结构（`video_sync.v`，参数选择，不用 generate）

```verilog
// DE/HS/VS 一起精确延迟 LATENCY 拍（每拍移 3 位，SRL32E）
always @(posedge clk) sr <= {sr[3*LATENCY-4:0], de_in, hs_in, vs_in};

// 像素：核输出写 FIFO（带抖动），按显示 DE 读出
wire we = gray_valid & ~full;      // 核有数据就写
wire re = de_del & (cnt != 0);     // 显示窗口内、非空才读

assign de_out  = USE_FIFO_OUT ? de_del   : gray_valid;
assign rgb_out = {3{(USE_FIFO_OUT ? pix_fifo : gray_in)}};
```

* `USE_FIFO_OUT = 0`（灰度 / MODE=0,2）→ 保持 f11b691 原语义（DE 跟 TVALID），已验证不动
* `USE_FIFO_OUT = 1`（高斯 / MODE=1）→ **编码器看到的 de/hs/vs 与输入完全同构**，只是整体晚 2205 拍；
  核的停顿/抖动全部被 512 深 FIFO 吸收，只影响个别像素位置，不再破坏锁相

## 13. v5.10：校准实验开关（MODE=3 / MODE=4）+ LATENCY 下限保护

### 13.1 为什么单独做这两个模式

`MODE=1`（正常高斯显示）走的是"DE/HS/VS 定长延迟 + 像素 FIFO"，
**在这条路径下改 `SYNC_LATENCY` 不会让画面错位**（只会因为 FIFO 读空而变黑）。
所以要做"只打 1 拍看错位"的实验，必须让 **DE 跟着核的 TVALID 走**（`USE_FIFO_OUT=0`），
这样 HS/VS 的延迟值才会直接体现成画面偏移量。

### 13.2 模式表（`hdmi_loop.v`）

|---|---|---|---|---|
| 0 | 灰度核 TVALID | 3 | 灰度验收 | — |

| 2 | 灰度核 TVALID | 3 | 灰度显示 + 高斯在跑 | — |

即 `LATENCY=1` 实际按 **2 拍**实现，对"看 2204 拍左右的错位"这个实验没有任何影响。

## 14. v6.0：模式表改为四档，新增锐化（模式3）

### 14.1 模式表（`hdmi_loop.v`）

| MODE | 含义 | 送编码器的像素 | DF/HS/VS | 延迟 |
|---|---|---|---|---|
| **0** | 直入直出 | `video_rgb` **纯直连，不打拍** | 直接用 hdmi_rx 输出 | 0 |
| **1** | 灰度 | `rgb2gray` | `USE_FIFO_OUT=0`，DE 跟核 TVALID | 3 拍 |
| **2** | 平滑 | `gauss3x3` | `USE_FIFO_OUT=1`（定长 DE + 像素 FIFO） | 2205 拍 |
| **3** | 锐化 | `clamp(2*gray − gauss)` | `USE_FIFO_OUT=1` | 2205 + 3 = **2208 拍** |

```verilog
localparam integer MODE         = 2;
localparam integer SHARP_PIPE   = 3;          // FIFO同步读1 + 算术1 + 限幅1
localparam integer SYNC_BASE    = 2205;       // gauss 核延迟（1 行 + 5 拍）
localparam integer USE_FIFO_OUT_M = (MODE == 2) || (MODE == 3);
localparam integer SYNC_LATENCY   = (MODE == 2) ? SYNC_BASE :
                                    (MODE == 3) ? SYNC_BASE + SHARP_PIPE : 3;
```

模式0 是厂家原始环回（`video_din(video_rgb)`、`video_de/hsync/vsync` 直连），
该构建下 `video_core/video_sync/video_dbg` 会被综合裁掉，资源最省。

### 14.2 锐化实现（`video_core.v`）

非锐化掩模：`sharp = orig + (orig − smooth) = 2*orig − smooth`，限幅 0~255。

**① 两路对齐：靠 FIFO 配对，不靠固定延迟**

```verilog
wire pwe = gray_valid & ~pfull;      // 写：灰度流
wire prd = gauss_valid & ~pempty;    // 读：高斯流（出一个弹一个）
```

- 深度 4096×8（同步读 → BRAM），实测峰值占用 **1928**（约 1.8 倍余量）；
- 高斯核每行多推进 1 次（1921 vs 1920）导致输出相对灰度流有 1~3 拍抖动，
  用"gauss 出一个像素就弹一个灰度像素"配对，抖动被 FIFO 天然吸收，
  不会像固定延迟链那样错 1~2 个像素。

**② 计算与限幅各占一拍（全时序逻辑）**

```verilog
// 第 1 级：2*orig − smooth（组合只到本寄存器输入端）
sum2_s1 <= $signed({1'b0, pair_dout, 1'b0}) - $signed({1'b0, gauss_d1});  // [−255,510]
vld_s1  <= pair_v1;
// 第 2 级：限幅 0~255
sharp_r <= (sum2_s1 < 0) ? 8'd0 : (sum2_s1 > 255) ? 8'd255 : sum2_s1[7:0];
sharp_v <= vld_s1;
```

数据与 valid 每级同沿推进 → 输出仍是"valid 与 data 同拍"，比 gauss 流晚 **3 拍**
（FIFO 同步读 1 拍 + 算术 1 拍 + 限幅 1 拍），顶层据此把 `SYNC_LATENCY` 定为 2208。

### 14.3 验证

| 项 | 结果 |
|---|---|

### 14.4 局限（写报告时说明）

- 图像边界：gauss 在左右/上下边缘按 0 补，`smooth < orig` →
  `sharp = 2*orig − smooth` 会把边界**提亮 1~2 像素**，属算法固有现象；
  如观感突兀可加"每行首尾 2 列/首末行屏蔽"。
- 增益固定 k=1（严格按题目 `orig + (orig − smooth)`），不做可调增益。
### 14.5 修正：模式2/3 的同步延迟按实测重算

上板发现**模式3 有左侧黑条 + 画面错位**，根因是延迟常量算错：

| 量 | 数值 | 依据 |
|---|---|---|
| gauss 流比输入 DE 晚 | **2211 拍** | `tb_offset`：LAT=2205 时相位偏移 **+6** → 2205+6 |
| sharp 流比 gauss 再晚 | **3 拍** | `tb_sharp`：gauss@2217 → sharp@2220 |
| sharp 真实延迟 | **2214 拍** | 2211+3 |

原来写成 `2205+3=2208`，比真实值少 6 拍 → DE 窗口比数据早到 → 每行开头读到空 FIFO：
**左侧 6 像素黑条 + 整行内容右移**（正是上板看到的现象）。

修正后：

```verilog
localparam integer SYNC_BASE   = 2211;   // 实测 gauss 延迟
localparam integer SYNC_MARGIN = 4;      // 余量：宁可左移几像素，也不要 DE 早到
localparam integer SYNC_LATENCY = (MODE == 2) ? SYNC_BASE + SYNC_MARGIN :          // 2215
                                  (MODE == 3) ? SYNC_BASE + SYNC_MARGIN + SHARP_PIPE : 3;  // 2218
```

`tb_offset` 里同时接了三路验证：`LAT=2215`（gauss）与 `LAT=2218`（sharp）相位偏移均为 **0 拍**。
两份新 bit：`hdmi_loop_MODE2_smooth.bit`（2215）、`hdmi_loop_MODE3_sharp.bit`（2218）。

## 15. v7.0：锐化改为 HLS 核内实现（`unsharp3x3`），k 可选

### 15.1 为什么放弃"RTL 外部配对"方案

v6.0 用 RTL 做 `sharp = 2*orig − smooth`，靠"灰度 FIFO 与高斯输出逐像素配对"。上板症状：

* 左边固定黑条（改延迟 2208/2218/2278/4414 **位置不变**）；
* 画面"两帧重写"（内容逐帧下移）；
* 修复 FIFO 深度后 `led[2]/led[3]`（欠载/溢出）**全灭**，症状仍在。

**真因**：高斯核每帧有一整行"只写不读"的补 0 行（内部 i=1080），它的 1920 个输出挤在
消隐期吐出 → 对齐 FIFO 里攒的 1920 个灰度像素被吃光（占用降到 0）→ 新帧开头
`pempty` 屏蔽约 1920 次配对 → **每帧少 1 行配对** → 内容逐帧滚动。
4096 深的像素 FIFO 吃掉这个缺口，所以 LED 指示不到。

**结论**：RTL 外部配对必须处理 HLS 核的帧边界行为，不可靠。

### 15.2 新方案：`unsharp3x3`（HLS 核内算）

`hls_prj\unsharp3x3\unsharp3x3.cpp`（从 gauss3x3 派生）：

```c
T1 center = wlb.getval(REF_ROWS / 2, REF_COLS / 2);   // 窗口中心 = orig
typedef ap_fixed<22,12> T4;                            // k=2 范围 [−510,765]
T4 sh = (T4)center + (T4)center + (T4)center - (T4)d - (T4)d;   // 3*orig − 2*smooth
if (sh < 0) dd = 0; else if (sh > 255) dd = 255; else dd = sh;
```

* **增益 k=2**：`sharp = orig + 2*(orig − smooth)`（k=1 时把两处算式改成 `2*orig − d` 即可）；
* csynth：**II=1**，流水 **6 级**（gauss 是 5 级）→ 比 gauss 多 1 拍，`SHARP_PIPE = 1`。

`video_core.v` 改为**两核并联**，各带 16 深弹性 FIFO：

```
rgb2gray ─┬─[16 深 FIFO]─> gauss3x3   ─> gauss_out
          └─[16 深 FIFO]─> unsharp3x3 ─> sharp_out
```

不再有任何跨核对齐；锐化流时序与已验证的平滑流完全同构。

### 15.3 验证

| 项 | 结果 |
|---|---|

| 数值验证（满幅台阶，`tb_unsharp_num.v`） | x=300：gray=219、gauss=164 → sharp = 3×219−2×164 = **329 → 限幅 255** ✓<br>x=299：gray=0、gauss=54 → sharp = −108 → **0** ✓（公式逐点吻合） |
| 上板（V8，k=1） | **无黑条、无重写** ✓；但 k=1 视觉上与灰度几乎无差别（线性渐变上是恒等变换） |
| 综合/实现（V8/V9） | 0 error / 0 critical warning；WNS 0.207 / 0.332 / 0.149 ns |

### 15.5 关于"看不出锐化效果"

* k=1 + 3×3 高斯（σ≈0.85）本身就是**很弱的锐化**；在线性渐变区域它是**恒等变换**
  （`gauss == gray` → `sharp == gray`），这是数学必然；
* 高对比边缘的过冲会被 0/255 限幅吃掉；
* 采集卡缩放预览会进一步抹掉 1 像素级的增强；
* 需要明显效果时用 **k=2（本次 V9）**，或把"平滑参考"换成 5×5 高斯。

## 16. v7.1：锐化核改成拉普拉斯核 `[0,-1,0; -1,5,-1; 0,-1,0]`

### 16.1 实现（`hls_prj\unsharp3x3\unsharp3x3.cpp`）

不再做"先高斯平滑再相减"，而是**直接与拉普拉斯锐化核卷积**（模板里的窗口/行缓存结构完全复用）：

```c
T2 ref[REF_ROWS][REF_COLS] = {
    {  0, -1,  0 },
    { -1,  5, -1 },
    {  0, -1,  0 }
};
typedef ap_fixed<22,12> T4;      // 取值 [−1020, 1275]，需 12 位整数位
T4 d;
...
d = 0;
for (ii) for (jj) d += (T4)ref[ii][jj] * (T4)wlb.getval(REF_ROWS-1-ii, REF_COLS-1-jj);

if (d < 0) dd = 0; else if (d > 255) dd = 255; else dd = d;
```

即 `out = 5*center − (up + down + left + right)`。

### 16.2 特性

| 输入 | 输出 | 说明 |
|---|---|---|
| 平坦区 | `5c − 4c = c` | **恒等**，不变亮也不变暗 |
| 线性渐变 | 恒等 | 与高斯平滑同性质 |
| 台阶边缘 | 过冲/欠冲 | 例：x=300 处 `5×219 − 657 = 438 → 限幅 255`；x=299 处 `−219 → 0` |

csynth：**II=1**、流水 **7 级**（gauss 5 级）→ `SHARP_PIPE = 2`，模式3 的
`SYNC_LATENCY = 2211 + 2 = 2213`。
