## 2. 理论问答与概念答疑记录（实验过程，报告素材）

### 2.1 vs / hs / de 是什么（同步信号）
- vs=垂直同步（场同步，帧起始标志）；hs=水平同步（行起始标志）；de=数据有效（de 为高时像素数据有效）
- 1080p@60 参数：每行 2200 拍（有效 1920）、每帧 1125 行（有效 1080）、像素时钟 148.5MHz（周期 6.73ns）
- HLS 式架构下同步全部由核外统一框架处理，核只接收像素流与帧尺寸参数

### 2.2 hls::stream<ap_uint<24>>&src 是什么
- 24 位宽硬件流（FIFO 语义）接口引用；src.read() 每拍取 1 个像素；综合为 AXI4-Stream（axis）接口
- 24bit=RGB888 一像素：R[23:16]、G[15:8]、B[7:0]

### 2.3 为什么必须用 stream（直接输入不可以吗）
- 实时视频是无界连续数据流，每像素时钟到达 1 个像素；标量只能传 1 个值，数组/指针需要完整存储或地址握手，均无法表达"每拍 1 像素"的连续流水
- stream 天然 FIFO：每拍可读写 1 个数据，直接映射到逐像素流水；RTL 侧综合为 axis 接口

### 2.4 Solution 周期如何设置
- Solution Settings → Synthesis Settings：Period=6.73ns（=1/148.5MHz）、Uncertainty=0.1、Part=xc7a35tfgg484-2

### 2.5 #pragma HLS INTERFACE ap_ctrl_none port=return 含义
- 去掉默认的 ap_start/ap_done/ap_idle/ap_ready 控制端口 → 核自由运行，外部无需启动/完成握手
- 配合 axis 接口实现"数据进来就处理、流水不停"的实时视频核

### 2.6 循环内声明变量不会重复声明吗
- 每次迭代是新的块作用域：同名变量在不同迭代是不同实例，生命周期不重叠 → 不冲突
- 综合后映射为同一组寄存器逐拍复用；声明位置不影响面积，只影响综合器依赖分析（利于 II=1）
- 例外：需跨迭代保持的状态（行缓存/窗口寄存器/累加器）必须声明在循环外——任务2高斯核 linebuf 是典型

### 2.7 #pragma HLS PIPELINE II=1 是不是"所有赋值并行执行"
- 不完全是：II=1 指相邻两次迭代启动间隔=1 拍，即每拍启动一个新迭代（吞吐=1 像素/拍）
- 循环流水让不同迭代的阶段重叠（装配线式）；同一迭代内语句仍按数据依赖串行（读→拆→算→写），无依赖的才并行
- 点操作依赖链短 → II=1 天然达成；窗口核需 ARRAY_PARTITION/DEPENDENCE 帮助压 II

### 2.8 拆位操作为什么不占一个周期
- p.range() 综合后是纯布线（从 24 位总线抽出 8 位），0 逻辑门、0 延迟
- 时钟周期=寄存器到寄存器的组合路径延迟预算；拆位/赋值不增加路径深度，被吸收进相邻运算（乘法/加法）
- 点操作核"个位数拍"延迟来自乘加链（66R+129G+25B），与拆位无关

### 6.2 讲解阶段沉淀（理论问答扩展，报告素材）
- HT_Window 坐标原点在右下、val[0][0]=最新像素 → 卷积取核 getval(2-ii,2-jj) 为坐标反转（中心对齐，非镜像）
- insert() 每拍动作：窗口右移 + 新像素双写（窗口+行缓存）+ 垂直取数 + 列推进 → 固有延迟≈1行+N拍（同步补偿标定对象）

- 动画 bug 教训：行缓存曾建为 3×W 列导致输出整体右移一列、无中心像素输出；修复为 3×(W+1) 列、col 与循环列 j 同步（set_size(W+1) 的含义）
- 卷积对齐：中心对齐，输出(i,j)=输入(i,j) 的平滑值，输出与输入同尺寸

### 6.3 与 RTL 基座工程的匹配判断（2026-11-04 侦察 vivado_prj/hdmi_loop）
- 顶层 hdmi_loop.v（115行）：u_hdmi_rx（HDMI 解码）→ video_rgb[23:0]+video_hs/vs/de → u_rgb2dvi_0（DVI 发送），直通环回；插入点在这两级之间

### 7.2 设计：video_sharp.v（GBK 无 BOM，可综合）
- 结构：gray_in(axis) → gauss3x3 IP → smooth；同源 gray_in → 原图对齐 FIFO → orig_dly；

- 对齐原理（关键）：
  - 核把 smooth 推迟约 (1行+K) 拍（K=5，csynth axis 迭代延迟，ILA 复核）

- 双路径同步：gray_tready = gauss_tready && !fifo_full，保证核读流与 FIFO 写入同拍同像素

### 10.1 需求与标定值

  - → HS/VS 合计补 **1 行 + 10 拍 = 2210 拍**（与实测 2211 差 1 拍，可忽略）
  - 若两核各算 1 行（2 行 + 10 拍 = 4410），HS/VS 会多推整 1 行 → 画面整体上下偏 1 行

### 10.2 关键认识（修正上一版的错误）
- 上一版 `DELAY = 1926` 的推导是"1 行（1921 拍）+ 5 拍"，把核内部的**计数拍数**当成了**时间轴拍数**
- 1921 = 1920 有效 + 行末补 0 列，只在核的平铺循环里成立；HS/VS 的实际时间轴是 **1 行 = 2200 拍**（1920 有效 + 280 行消隐，1080p60）
- 按 1921 算：每行少补 279 拍，两行累计 **558 拍 > 280 拍行消隐** → HS 脉冲滑进有效像素区中间，画面撕裂/整体偏移
- 结论：**行级 → 按整行周期（LINE_CLKS=2200）算；拍级 → 按 csynth 迭代延迟算**，两者分开参数化

### 10.3 代码改动（`video_sync.v` + `video_core.v` + 顶层）
- `video_sync`：单参数 `DELAY` → 两级参数 `LINE_CLKS / GRAY_LINE / GRAY_TAP / GAUSS_LINE / GAUSS_TAP`；
  `D_GRAY = 0×2200+4 = 4`、`D_GAUSS = 1×2200+6 = 2206`、`D_TOTAL = 2210`
- 结构：`hs_vs_dly`（分布式 RAM 环形缓冲）**级联两级**——原始 → 灰度级（4 拍）→ 高斯级（再 2206 拍）；
  新增 `hs_gray/vs_gray` 抽头，任务4「模式1 只看灰度」可直接用
- 不变的两条原则：`de_out = smooth_valid`（跟末级核 TVALID）、`rgb_out = {3{smooth_in}}`（像素组合直通）
- 顺带修 bug：旧环形缓冲用 `$clog2(DELAY)` = 11 位计数器按 2048 回绕，而 RAM 只有 1926 深 → 地址 1926~2047 越界，
  每 2048 拍有 122 拍读到无效值。新版深度取 `DELAY+1`、按 `DEPTH` 回绕、读指针超前 1 格，读写永不同址

### 10.3 三个真根因（报告核心素材）
1. **XDC 漏像素时钟约束**：pixel_clk 未约束 → 高斯核（BRAM 行缓存 + 加法树 + col 逻辑）未约束必崩
   （已布线网表补约束实测 WNS **−2.233ns**、311 条违例路径）；灰度浅逻辑"侥幸能跑"→ 症状"仿真全过、上板只有灰度能动"。
   修法：create_clock -period 6.734 -name pixel_clk [get_nets pixel_clk] + 异步时钟组 + 时序器复位 set_false_path。
2. **大延迟用 FIFO + data_count 实现不可靠**：延迟多 1~2 拍且语义不确定 → 改**无 for、无复位的 SRL 移位链**
   （eg [2*LATENCY-1:0] sr <= {sr[..], hs_in, vs_in}，综合成 SRL32E 链，延迟严格 = LATENCY，不加复位才不会退化成触发器阵列）。
3. **DE 不能直接接核 TVALID**：gauss3x3 每行需 1921 次流水推进（1920 读 + 行末补0）而视频每行只 1920 拍
   → dst TVALID 天生带气泡、相位抖动；与定长 HS/VS 相对位置不稳 → 显示器锁不住 →"有数据但无画面"。
   修法：USE_FIFO_OUT=1 —— DE/HS/VS 三者一起精确延迟 2205 拍 + 像素写 512 深 FIFO、按显示 DE 读出，
   编码器看到的行/场结构与输入**完全同构**；USE_FIFO_OUT=0（灰度）保持 f11b691 原语义不动。

### 10.4 与任务1 同步方案的关键差异（重要认知修正）
- 任务1（灰度，3 拍，点操作核）：DE 跟随核 TVALID 有效（无行缓存、TVALID 稳定）——§8 结论**仅适用该场景**
- 任务2（高斯，1 行+K，行缓存核）：**DE 必须定长延迟 + 像素 FIFO 重定时**（TVALID 抖动）
  → "DE=TVALID"原则不能跨类套用；行缓存核的输出必须 FIFO 重定时
- 延迟量纲：HS/VS 延迟按**视频时间域行周期 2200 拍**（含消隐）计，非处理流的 1921 拍
  → SYNC_LATENCY = 2205（=1 行 2200 + 5 拍流水），而非早先估算的 1926

### 10.5 其他工程要点
- **两核之间 16 深弹性 FIFO**：吸收高斯每行 1 拍反压；若两核直连，灰度核每行丢 1 像素 → 1080 像素/帧
  → 核行场相位逐帧漂移 ≈0.56 行/帧 → 数帧后"第 0 行不出数"空窗漂进可见区 → **无信号**。
  实测 FIFO 峰值占用仅 2，DE/line 从 1919 恢复 1920。
- **灰度核 dst TREADY 恒 1'b1**（不反压）：通路不依赖下游，也防综合器把未选中的核当 unused 裁掉
  （Synth 8-3332 裁核 → src TREADY 悬空常 0 → 上游被永久顶住 → 画面死）
- FIFO 读使能必须带非空：ifo_rd = gauss_src_rdy & ~fifo_empty（否则空读下溢→假满→溢出丢像素）
- 误删 .gray_valid 一根连线 → LUT 从 872 掉到 337、高斯核被裁 → **综合前后资源/告警对比可抓连线级错误**

## §11 “同步只打 1 拍”错位复现实验（仿真替代上板，报告必答项）

### 11.1 实验设置（缩小同构，比例与 1080p 一致）

| 帧有效行 / 消隐行 | 1080 / 45 | 7 / 3 |
| 核延迟 D（=1 行 + 5 拍） | 2205 拍 | 45 拍 |

### 11.2 实测结果
| 通道 | 同步延迟 | 空读（黑边）拍数 | 稳态样本 | 偏移 Δ（内容落后） | 结论 |
|---|---|---|---|---|---|
| CHA | 1 拍 | 37 | 529 | **37 拍 = 1 行 + 5 列**（min=max=37 恒定） | 固定错位 |
| CHB | 45 拍 | 1 | 493 | 1 拍 = 0 行 + 1 列（FIFO 组合读视图残差） | 对齐 |

### 11.3 理论对照（关键认知修正）
- **错位量的正确算法**：不是 D − 同步延迟 = 44（按时间轴拍数算，得 1 行 4 列——错），
  而是**核延迟窗口内流入 FIFO 的有效像素数**：D 窗口 45 拍里有 8 拍行消隐不产生像素 →
  有效 = 32 + 5 = **37 拍 = 1 行 5 列**（与实测完全一致）。
- **1080p 同构换算**：D = 2205 拍窗口内 = 1920（第 1 行有效）+ 5（第 2 行前 5 拍）= **1925 拍 = 1 行 + 5 列**
  （消隐 280 拍不产生像素，故不是 2204 = 1 行 4 列）。
- 两个数字不矛盾：**时间轴**延迟 2205 拍（含消隐）= **像素域**延迟 1925（1 行 1920 + 5 拍）。
  SYNC_LATENCY=2205 与像素错位 1 行 5 列描述的是同一件事。

### 11.4 上板应看到的现象（报告可用表述）
“同步只打 1 拍时，屏幕上图像**整体向右下偏移 1 行 5 列**：顶部 1 行与左侧 5 列显示的是上一帧末尾的拖尾内容，底部 1 行与右侧 5 列的原图内容被挤出画面。偏移量恒定、不随帧变化（不是漂移），说明是‘同步与数据的固定相位差’，与‘帧边界不同步’的抖动型故障可区分。”

### 11.5 结论（可直接写进报告的论证）
1. 窗口核（延迟 ≈1 行 + N 拍）**不能像点操作核那样把同步直通/只打 1 拍**：任何小于核延迟的同步补偿都会留下“核延迟 − 同步延迟”的固定像素偏移，1 行 5 列的量级远超肉眼可容忍范围（1 列才可忽略）。
2. 正确做法 = 等延迟匹配：HS/VS/DE 给定长延迟，深度按实测 D（2205 拍）设置，同时用像素 FIFO 把核的抖动输出重定时到显示节拍（v5.9 USE_FIFO_OUT=1）。
3. 等延迟匹配后残余 1 拍的 1 列误差来自“自建 FIFO 写读同拍不可见”的视图偏差（本 tb CHB 实测 Δ=1）；1080p 下 1 列不可见，若要求严格 0 偏差可把同步深度改为 D+1 或改用 FWFT（first-word fall-through）FIFO。
4. 与 v5.9 实板对照：灰度核（3 拍，DE 直接跟随 TVALID）无此错位；高斯核一旦同步补偿不对，实测“有数据但无画面/整体偏移”，与仿真复现的固定偏移同源。
