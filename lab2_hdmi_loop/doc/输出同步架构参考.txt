输出同步架构参考（实验二·总体架构方案）
回答一个问题：带行缓存的处理核（平滑/锐化）插进 HDMI 环路后，画面为什么错位，总体上怎么解决。 本文只讲两种总体架构的思路与选型，不含实现细节——细节在你选定架构后再查指导书对应任务与参考工程。
1 问题的一句话
点操作核（灰度）每个输出像素只依赖当前输入像素，进出节奏一致，插进环路画面纹丝不动；3×3 窗口核必须"先吃进约 1 行才能吐出第一个像素"——输出数据比输入滞后了好几拍，而输出同步信号如果还按输入的节奏发，画面就会整体偏移、撕裂或帧尾拖尾。
解决思路只有两条路：要么让同步信号跟着数据一起走（video 架构），要么把同步问题交给一个与算法无关的统一框架（hls 架构）。
2 架构一：video 式——同步信号随数据流水
HDMI-IN ──► ┌─────────────────────────────┐ ──► HDMI-OUT
(数据+同步) │  HLS 处理核                  │  (数据+同步)
│  接口 = 像素 + de/hs/vs 一组  │
│  同步信号在核内随数据打拍传递  │
└─────────────────────────────┘
思想：把 de/hs/vs 当作"随行行李"——与像素同进同出。核内部流水多深，同步就跟着滞后多深，于是输出端的数据与同步永远天然对齐，下游编码器拿到的就是一套自洽的时序，不需要任何外部补偿。
总体特点：
三个核（灰度/平滑/锐化）可以像积木一样直接级联，核与核之间不需要任何胶合逻辑；
点操作核几乎零额外工作；窗口核的行缓存就在核内，输出节奏由核自己保证；
接口风格与基座连线最直接——顶层把"数据+同步"一组线从接收模块改接到处理核再回发送模块即可；
需要注意的一点：核在帧头"吃进"的额外行会让输出帧的节奏整体滞后，核输出侧要保证每帧吐出的有效行数正确（即"账要平"）。
你的现成参考：gamma 参考实现（hls_video_gamma）就是这个接口风格——顶层函数参数里像素与 hs/vs/de 并排出入；课程配套已验证的融合工程也是此风格。
3 架构二：hls 式——纯流式核 + 外部统一同步框架
HDMI-IN ──► 像素流 ──► ┌──────────────┐ ──► ┌──────────────────────┐ ──► HDMI-OUT
(数据+同步)  提取同步   │ HLS 处理核    │像素流│ 外部同步框架          │
│ (只管算法,    │     │ 延迟标定 → FIFO 缓冲  │
│  接口=纯像素流)│     │ → 按标定值出队 → 每帧 │
└──────────────┘     │ 冲刷自愈             │
└──────────────────────┘
思想：核保持纯算法——接口只有像素流，不带任何同步概念（参考实现 gray8_gauss2d_3x3 正是这种接口，任何分辨率通吃）。同步问题集中到核外一个与算法无关的框架里一次解决，其总体逻辑四句话：
每帧开始时标定本帧核的实际延迟；
输出数据先进 FIFO 缓冲，不直接上路；
同步域按标定的延迟值出队——数据和同步在正确的相对位置重新会合；
每帧结束冲刷一次，任何误差都不跨帧累积、系统自愈。
总体特点：
核完全通用、可移植：换个分辨率、换个系统，核一行不用改；
同步逻辑一处写好处处复用，且对"核内部怎么实现"零假设——黑盒即插；
代价是要读懂并搭出这个框架（它比核本身更需要视频时序的理解）。
你的现成参考：该架构已在配套融合工程中实测跑通（四种模式仿真位精确通过，每帧 2,073,600 像素即 1920×1080 逐帧核算精确吻合）——这是一条经过实战验证的路径。

实验二建议：默认走 video 式——与基座连线最直接，灰度核几乎零同步工作，平滑/锐化沿用参考实现的纯流式接口时，在核外薄薄包一层"同步进→像素流→同步出"的壳即可；把两种核都做完后，若想深入理解同步问题本身，再尝试 hls 式框架（它会让你真正读懂"节奏"二字）。
验收标准两种架构完全一致：四模式画面正确、空间对齐、无拖尾不渗帧——架构只是手段。
5 一句话方法论
同步的本质是让输出数据与输出同步信号说同一种节奏：要么让它们结伴同行（video 式），要么建一个专门校准节奏的驿站（hls 式）。选哪条路，先看你想在"核"里花力气，还是想在"框架"里花力气。
