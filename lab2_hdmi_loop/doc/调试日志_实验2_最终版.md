## 1. 系统结构（最终版）

```
                     ┌──────────────────────── video_core.v ────────────────────────┐
HDMI IN ─> hdmi_rx ──┤ rgb2gray ─┬──────────────────────────────> gray_out          │
          video_rgb   │           ├─[16 深弹性 FIFO]─> gauss3x3   ──> gauss_out      │──> video_sync.v ──> hdmi_tx ──> HDMI OUT
          video_de    │           └─[16 深弹性 FIFO]─> unsharp3x3 ──> sharp_out      │    (hs/vs SRL 延迟链
          video_hs    └────────────────────────────────────────────────────────────────┘     + DE 定长延迟
          video_vs                                                                          + 4096 深像素 FIFO)
```

| 核 | 功能 | 系数 | II | 流水 | Latency | Trip Count |

## 2. 关键参数一览

```verilog
// hdmi_loop.v
localparam integer MODE         = 3;      // 0=直通 1=灰度 2=平滑 3=锐化
localparam integer SYNC_BASE    = 2211;   // 实测：gauss 流比输入 DE 晚 2211 拍
localparam integer SYNC_MARGIN  = 0;      // 留余量只会把黑条从左边缘挪到右边缘
localparam integer SHARP_PIPE   = 2;      // 锐化核比高斯核多 2 级流水
localparam integer USE_FIFO_OUT_M = (MODE == 2) || (MODE == 3);
localparam integer SYNC_LATENCY   = (MODE == 2) ? SYNC_BASE + SYNC_MARGIN :              // 2211
                                    (MODE == 3) ? SYNC_BASE + SYNC_MARGIN + SHARP_PIPE : 3;  // 2213
```

```verilog
// video_sync.v
localparam integer LAT = (LATENCY < 2) ? 2 : LATENCY;   // 防 LATENCY=1 时位选出错
localparam integer FW  = 12;                            // 像素 FIFO 4096 深（≥一整行）
assign und_evt = USE_FIFO_OUT ? (de_del & (cnt == 0)) : 1'b0;   // 欠载 -> 黑像素
assign ovf_evt = USE_FIFO_OUT ? (gray_valid & full)  : 1'b0;    // 溢出 -> 撕裂
```

```verilog
// video_core.v：每个核前一个 16 深弹性 FIFO（吸收核每行 1 拍反压）
localparam integer FW = 4;      // 16 深
```

## 4. 根因汇总（5 条，按影响排序）

### 根因①：XDC 缺像素时钟约束 —— 决定性

`create_clock -period 6.734 -name pixel_clk [get_nets pixel_clk]` 缺失时，
高斯核整条路径不受时序约束，实现后 slack **−2.233 ns、311 条违例**，上板表现为花屏/无信号。
补上后 0 违例、出图正常。**这是"灰度正常但高斯无信号"的最终解释**。

### 根因②：用 `FIFO + data_count` 做延迟不可靠

早期用 FIFO 的 `data_count` 判断"攒够多少再读"，但异步 FIFO 的读延迟与 `data_count`
更新时刻不确定 → 相位随机漂移。改成 **3 bit 打包进 SRL 移位链**（`sr <= {sr[3*LAT-4:0], de, hs, vs}`）
后，延迟精确到拍。

### 根因③：DE 不能直接接核的 `TVALID`

HLS 核 `II=1` 的流水只有一套使能：`src` 空时**整条流水冻结**，行末会出现 1~3 拍气泡
（实测 12 进 11 出）。若 `DE = TVALID`，显示窗口会随气泡抖动。
改为"**输入 DE 定长延迟做窗口 + 像素走 FIFO**"，把气泡交给 FIFO 吸收。

### 根因④：像素 FIFO 深度不足 → 每帧溢出 → 画面撕裂

高斯核每帧有一整行"**只写不读**"的补 0 行（内部 `i = 1080`，`j` 循环 1921 次），
它的 **1920 个输出挤在消隐期吐出**；消隐期显示端不读 → **512 深的 FIFO 装不下**
→ 每帧溢出约 1400 个像素 → 上一帧内容混进帧首（"两帧重写"）。
修法：`video_sync` 像素 FIFO 加深到 **4096**（≥ 一整行）。

### 根因⑤：RTL 外部配对的锐化方案，在帧边界必然丢行

详见 §11.3（已废弃方案）。结论：**锐化必须放进 HLS 核内算**。

```

在途像素 = 1925（= 核整条流水延迟，单位拍）
```

## 6. 为什么"高斯/锐化看起来不明显"

1. **3×3 高斯 σ≈0.85**，只平滑 1~2 像素，1080p 观感接近清晰；
2. **拉普拉斯核在平坦区和线性渐变上是恒等变换**（`5c − 4c = c`）——斜坡测试图上必然与灰度一致，
   只有边缘才出效果（这是数学必然，不是 bug）；
3. **过冲被 0/255 限幅吃掉**一部分；
4. **采集卡预览会缩放**，把 1 像素级的增强抹平；
5. 想明显看到效果：看**文字边缘 / 细纹理 / 棋盘格**，或把核换成更强锐化 `[-1 -1 -1; -1 9 -1; -1 -1 -1]`。

## 8. 板级诊断手段

### 8.1 LED 仪表（最有效，绕开 JTAG）

| LED | 含义 | 判读 |
|:--:|---|---|
| `led[0]` | 高斯核上一帧有出数 | 常亮 = gauss 有输出 |
| `led[1]` | 灰度核上一帧有出数 | 常亮 = gray 有输出 |
| `led[2]` | **本帧出现过欠载**（DE 读到空 FIFO） | 亮 → 左黑条 → 延迟给小了 |
| `led[3]` | **本帧出现过溢出**（FIFO 满丢像素） | 亮 → 撕裂 → 深度不够 |

> 这两颗灯是定位 §4 根因④⑤的关键：V7 三档（2214/2278/4414）两灯全灭而症状仍在
> → 证明问题不在 FIFO，而在配对逻辑 → 最终找到帧边界丢行。

### 8.2 ILA（三次失败，供参考）

| 报错 | 原因 | 处理 |
|---|---|---|
| `no supported debug core(s)` | bit 里没有 ILA | 用带 ILA 的构建 |
| `debug hub core was not detected` | hub 时钟 `pixel_clk` 未在跑 | 必须 HDMI 输入在线（有像素时钟） |
| `Mismatch ... hw_probe 'dbg_gauss_beats' port index '4'` | 旧探针文件残留 | 下 bit 前先 `refresh_hw_device -update_hw_probes false`，bit 与 `.ltx` **同批**生成并一起下 |

### 8.3 白条调试踩坑

曾用 `DBG_BAR` 在画面里画白条做标记，两次全白：`vs` 极性搞反 + 计数器位宽饱和
（`beats[23:13]` 最大 2047 > 1920）。最终**关闭 `DBG_BAR`，改用 LED**。

## 11. 已废弃方案存档（写报告时的"弯路"）

### 11.1 v4.0 / v4.1："两级同步 + 输入 FIFO"

把输入像素先写 FIFO，再用输出侧的计数器按 `hs/vs` 重新读出。**上板无信号**。
原因：两级同步的相位关系无法保证，且缺少像素时钟约束。整版推翻，回到厂家骨架。

### 11.2 v5.10 校准实验（MODE=3/4/5）：接收端对相位不敏感

| 档 | DE/HS 相位改动 | 结果 |
|---|---|---|
| MODE=3 | DE 只打 1 拍 | 正常出图 |
| MODE=4 | DE 定长 2205 拍 | 正常出图 |
| MODE=5 | 半行偏移 | 正常出图 |

**结论：采集卡 + PotPlayer 会按 DE 自适应，hs↔DE 相位改 1100/2205 拍都看不出错位。**
所以"靠看画面判断同步对不对"是不可行的 —— 必须用 LED/仿真量数据。
（这组校准档后来已删除，模式表让位给 0/1/2/3。）

### 11.3 v6.0：RTL 外部配对做锐化 —— 帧边界必丢一行

**做法**：RTL 里 `sharp = 2*orig − smooth`；灰度流写一个 4096 深 FIFO，
高斯流出一个就弹一个灰度像素与之配对，两级流水（算术 1 拍 + 限幅 1 拍）。

**上板症状**：
* 左边固定黑条，改 `SYNC_LATENCY`（2208 / 2218 / 2278 / 4414）**位置不变**；
* 画面"两帧重写"（内容逐帧下移）；
* 修好 FIFO 深度后 `led[2]/led[3]`（欠载/溢出）**全灭**，症状仍在。

**根因**：高斯核每帧有一整行"只写不读"的补 0 行（内部 `i = 1080`），它的 1920 个输出
挤在消隐期吐出 → 对齐 FIFO 里攒的 1920 个灰度像素被吃光（占用降到 0）→ 新帧开头
`pempty` 屏蔽约 1920 次配对 → **每帧少 1 行配对** → 内容逐帧滚动。
4096 深的像素 FIFO 又把这个缺口吸收掉，所以 LED 指示不到。

**结论**：跨核对齐必须处理 HLS 核的帧边界行为，RTL 侧不可靠 → **锐化搬进核内**（v7.0）。

### 11.4 v7.0：非锐化掩模（`unsharp3x3` 第一版）

核内 `sharp = orig + (orig − smooth)`（k=1），结构上完全正确（无黑条、无错位），
但**视觉上与灰度几乎无差别** —— k=1 + 3×3 高斯本身就是很弱的锐化，
且在线性渐变上是恒等变换。后改为 k=2（`3*orig − 2*smooth`）用于对照，最终选择拉普拉斯核（v7.1）。

## 12. 经验总结（可直接写进报告）

1. **时钟约束是第一优先级**：没有 `create_clock`，综合/实现"能过"，但时序是假的，
   上板表现为"某个模式无信号"这种极难定位的症状。四档设计中同一路径在有无约束下
   差别是 −2.233 ns vs +0.15 ns。
2. **HLS 核的"行末气泡"和"帧边界补 0 行"是两个必须建模的行为**：
   前者用弹性 FIFO 吸收，后者决定了后续 FIFO 的最小深度（≥ 一整行 = 1920）。
3. **能用仪表量就不要用眼睛看**：接收端会自适应，画面看不出 10 拍级相位差；
   板载 LED（欠载/溢出）、ILA、仿真计数是唯一可靠的判断依据。
4. **跨模块配对要谨慎**：把"两个数据流按拍配对"放在 RTL 里，一旦上游有帧边界行为就会
   每帧系统性丢失，且被下游 FIFO 掩盖成"偶发错位"。正确做法是**把相关运算放进同一个核**。
5. **延迟常数要测不要猜**：`SYNC_BASE=2211` 由 `tb_offset` 相位扫描得出（`2205 + 偏移 6`），
   不是从"1 行 + 5 拍"估算来的；估算值与实测值差 6 拍就足以产生可见黑条。
6. **仿真要跨帧**：只跑 6~8 行的 testbench 测不出"每帧少 1 行"这类缺陷，
   `tb_sharp_full` 的 1080 行整帧计数才是有效的回归。

## 14. 任务四：按键运行时切换模式（v8.0）

### 14.1 设计

| 项 | 内容 |
|---|---|
| 顶层端口 | `input [3:0] key`（按下为低），`key[0]` 切模式 |
| 新增模块 | `sources_1/new/key_mode.v`：2 级同步 + 15 ms 计数消抖 + 边沿检测 + 模 4 格雷码计数 |
| 四档并存 | 三路 `video_sync` 并行：`u_sync_gray`(3) / `u_sync_gauss`(2211) / `u_sync_sharp`(2213)，4 选 1 mux 后统一打 1 拍送编码器 |
| LED | `led[1:0]`=模式号（sys 域），`led[2]`=当前档欠载，`led[3]`=当前档溢出 |
| 为什么用三个例化 | `video_sync` 的 `LATENCY`/`USE_FIFO_OUT` 是**参数**（编译期），运行时改延迟需要 RAM 延迟线；三路并行 + 输出 mux 改动小、且与已验证的单路结构完全相同 |

### 14.2 消抖与跨时钟域

* **计数消抖**：电平需稳定 **15 ms**（50 MHz → 750,000 拍）才承认；抖动期计数器反复清零；
* **边沿检测**：只在「未按 → 按下」的消抖后跳变出 1 拍脉冲 → 长按不连跳；
* **格雷码跨域**：模式计数步进 `00→01→11→10→00`，每步只变 1 位 →
  `pixel_clk` 域用 2 级同步器即可，不会出现非法中间码；
* 消抖时钟用 **`sys_clk`(50 MHz 独立晶振)**，与 HDMI 输入无关 → 没有 HDMI 时按键照样能改模式、LED 照样变。

### 14.3 XDC（引脚抄自达芬奇官方 `DaVinci_FPGA_IO.xdc`）

```tcl
set_property -dict {PACKAGE_PIN T1 IOSTANDARD LVCMOS33} [get_ports {key[0]}]
set_property -dict {PACKAGE_PIN U1 IOSTANDARD LVCMOS33} [get_ports {key[1]}]
set_property -dict {PACKAGE_PIN W2 IOSTANDARD LVCMOS33} [get_ports {key[2]}]
set_property -dict {PACKAGE_PIN T3 IOSTANDARD LVCMOS33} [get_ports {key[3]}]
```

`sys_clk` = **R4**，`create_clock -period 20.000`（原本已在 XDC 里）。

### 14.4 两个新踩的坑

**坑①：跨域路径被当成同域时序 → WNS −3.392 ns**

```
Source:      u_key_mode/mode_gray_reg[1]/C   (sys_clk, 20ns)
Destination: mode_meta_reg[0]/D              (pixel_clk, 6.734ns)
Requirement: 0.062ns   Slack: -3.392ns
```

修法：把四个时钟域声明为异步（原来只 group 了 pixel_clk 与两个 mmcm 输出，漏了 sys_clk，且
`get_clocks clk_out1_mmcm` 在综合阶段还不存在 → 那条约束本来就没生效）：

```tcl
set_clock_groups -asynchronous \
    -group [get_clocks -of_objects [get_nets pixel_clk]] \
    -group [get_clocks -of_objects [get_ports sys_clk]] \
    -group [get_clocks clk_out1_mmcm] \
    -group [get_clocks clk_out2_mmcm]
```

**坑②：XDC 不支持 `if` 语句**

我先写成 `if {[llength $mmcm_clks] > 0} { set_clock_groups ... }` 想做得稳一点，结果报
`CRITICAL WARNING: [Designutils 20-1307] Command 'if' is not supported in the xdc constraint file`，
**整段约束被忽略** → WNS 反而恶化到 **−4.726 ns**（连 hdmi_rx 内部的同步器路径都没被 cut）。
去掉 `if`、写 plain 语句后：**WNS +0.374 ns，0 违例路径**。

> 教训：XDC 只支持有限的 Tcl 子集（`set_property` / `create_clock` / `set_clock_groups` 等直接语句），
> 不要写 `if`/`foreach`/`proc`。需要条件逻辑就分环境维护约束文件，或写 tcl 脚本在综合前 source。
